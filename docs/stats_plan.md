# Podcast download statistics plan

## Goal

Measure podcast usage from requests for the published MP3 files. For this project,
we will use **downloaded audio as the listening metric**. This intentionally does
not attempt to measure playback position in a podcast application.

The first version should answer:

- How many downloads did each episode receive?
- How many approximate unique listeners were there?
- Which podcast applications and devices connected?
- How much audio data was downloaded?
- Which downloads were complete or partial?

## Existing deployment

The published site is static content served by Caddy and exposed through a
Cloudflare Tunnel. The RSS feed and MP3 files are generated by the publishing
pipeline and mounted into the Caddy container. There is currently no application
server or database in this Compose project.

Use an existing PostgreSQL installation rather than adding another database
container. The statistics collector can be a small companion service or a
scheduled importer running on the host.

## Recommended architecture

```text
Podcast app/browser
        |
        | GET /<token>/media/<episode>-<hash>.mp3
        v
Cloudflare Tunnel -> Caddy
                         |
                         | structured access log
                         v
                 scheduled importer
                         |
                         v
                    PostgreSQL
```

The simplest first implementation is batch-oriented:

1. Configure Caddy to emit JSON access logs for the published site.
2. Write logs to a persistent host-mounted directory, or retain them through
   Docker logging.
3. Run an importer periodically, for example every five minutes or hourly.
4. Insert raw request rows into PostgreSQL with a uniqueness key so retries of
   the same log entry are harmless.
5. Build reports and views from the raw rows rather than trying to update
   counters during the request.

Do not make Caddy call PostgreSQL synchronously. Serving audio must remain
independent of statistics availability.

## Caching policy

Disable Cloudflare caching for the MP3 paths initially. This ensures that each
download reaches Caddy and appears in the access log. It costs origin bandwidth,
but gives a complete and easy-to-explain dataset.

If bandwidth later becomes material, re-enable media caching and collect request
logs at the Cloudflare edge instead. Origin Caddy logs cannot count requests
served entirely from Cloudflare cache.

The RSS feed and HTML pages may remain cacheable according to the existing
policy; only media requests are relevant to this metric.

## Request data to retain

For each relevant successful `GET` or `HEAD` request, retain:

- event timestamp;
- normalized episode identifier derived from the media path;
- request method and status code;
- response bytes;
- requested byte range, when present;
- user-agent string;
- a short-lived or rotating hash of the client IP and user agent;
- an importer/log-entry identifier for idempotency.

Do not store raw IP addresses in the statistics database. The hashed value is an
approximate listener identifier, not an account identity. It will undercount
listeners who share an address and overcount listeners who change networks or
devices.

Ignore requests for HTML, artwork, RSS, robots.txt, and research pages. A `HEAD`
request can be useful for diagnostics but should not count as downloaded audio.

## Initial database shape

Keep the raw request data because podcast applications commonly use byte-range
requests, retries, and resumptions.

```sql
CREATE TABLE podcast_downloads (
    id                 bigserial PRIMARY KEY,
    observed_at        timestamptz NOT NULL,
    episode_id         text NOT NULL,
    method             text NOT NULL,
    status_code        integer NOT NULL,
    bytes_sent         bigint NOT NULL DEFAULT 0,
    range_start        bigint,
    range_end          bigint,
    user_agent         text,
    listener_hash      text,
    source_log_id      text NOT NULL UNIQUE
);

CREATE INDEX podcast_downloads_episode_time_idx
    ON podcast_downloads (episode_id, observed_at);

CREATE INDEX podcast_downloads_listener_time_idx
    ON podcast_downloads (listener_hash, observed_at);
```

The importer should only insert successful media responses, initially `200` and
`206`. Preserve the original status and range fields so the counting rules can
be refined without collecting new data.

## Counting rules

Start with simple, explicit metrics:

- **Download:** one successful `GET` media request.
- **Audio bytes:** sum of `bytes_sent` for successful media `GET`s.
- **Approximate unique listener:** distinct `listener_hash` during a selected
  time window.
- **Complete download:** a `200` response whose bytes sent are at least the
  known MP3 size, or a set of ranges covering that size when this can be
  reconstructed reliably.
- **Episode popularity:** download count and unique-listener count grouped by
  episode and day.

Do not deduplicate too aggressively in the first version. A retry or resume is
still useful evidence that an application requested the audio. Reports can later
add a sessionization window, such as grouping requests with the same listener
hash and episode when they occur within 24 hours.

## Podcast application information

Use the user-agent string to report clients such as Apple Podcasts, AntennaPod,
Overcast, or a web browser. Keep the original value in raw data and add a small
parser/view for normalized categories. User-agent identification is heuristic
and should be reported as such.

## Privacy and operational boundaries

- Publish aggregate statistics only; never expose listener hashes or raw user
  agents publicly.
- Document that download counts are estimates of listening under the chosen
  project assumption.
- Set a retention period for raw request rows, such as 90 days, and retain only
  daily aggregates afterward if long-term trends are needed.
- Give the importer a PostgreSQL role limited to its own schema and insert/read
  access required for reports.
- Keep the database connection string and any log credentials in ignored secret
  files or the existing secret-management system.
- Add monitoring for importer lag and parse failures; an importer failure must
  not affect Caddy or audio delivery.

## Implementation order

1. Add Caddy JSON access logging with a persistent log destination.
2. Disable Cloudflare caching for the MP3 path and verify that a test request
   reaches Caddy.
3. Create the PostgreSQL schema and a least-privilege database role.
4. Implement the importer with restart-safe log offsets and `source_log_id`
   deduplication.
5. Test normal, range, retry, missing-file, and non-media requests.
6. Add SQL views or a small report for daily downloads, unique listeners, bytes,
   user-agent categories, and completion estimates.
7. Revisit caching only after comparing bandwidth cost with the value of complete
   origin-side statistics.

## What this will not measure

This plan cannot prove that audio was heard. It will count requested/downloaded
data according to the project decision. It also cannot identify a person without
accounts or consent-based identity, and it will not capture requests served from
cache if media caching is later enabled without an edge-log integration.
